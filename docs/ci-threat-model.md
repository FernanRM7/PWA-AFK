# Matriz de amenazas y controles de CI

## Alcance

La matriz cubre el flujo de CI y la futura sincronización de inspecciones. Cada amenaza tiene un control y una verificación reproducible. Cuando una capacidad aún no está implementada, la prueba se marca como futura y no se presenta como evidencia actual.

| Amenaza | Activo afectado | Control | Prueba o comando | Resultado esperado | Prioridad y justificación | Riesgo residual |
|---|---|---|---|---|---|---|
| Un usuario consulta o modifica inspecciones fuera de su rol, propietario o asignación. | Inspecciones, hallazgos y cambios de estado. | Autorización por rol, propietario y asignación en cada lectura y escritura; denegar por defecto y comprobar autorización en el servidor. | Futura: `npm run test:auth -- --run` con casos de rol sin permiso, propietario distinto y asignación válida. Revisar que cada operación no autorizada responda `403`. | Sólo el rol permitido con propietario o asignación válida puede operar; los demás reciben `403` y no se modifica el registro. | **Alta**: una autorización incorrecta expone o altera datos de mantenimiento. | Persisten errores de configuración de roles, asignaciones obsoletas o bypass en una ruta nueva; requiere revisión por PR y pruebas negativas por endpoint. |
| Una reintento de sincronización crea duplicados o acepta una versión antigua del registro. | Cola local, registros sincronizados y consistencia del estado. | Identificador de operación único, idempotencia en servidor y validación de versión/timestamp; rechazar conflictos explícitamente. | Futura: `npm run test:sync -- --run`; repetir la misma operación y enviar una versión menor que la almacenada. | El primer envío se aplica una vez; el reintento devuelve el mismo resultado sin duplicar; la versión antigua se rechaza o se marca como conflicto. | **Alta**: duplicados o pérdida de la última actualización dañan la trazabilidad de inspecciones. | Conflictos simultáneos o relojes desalineados pueden requerir reconciliación manual; no se cubre hasta implementar backend y sincronización. |
| Una credencial real entra al repositorio, a un artefacto o a los logs de CI. | Código fuente, historial, artefactos y registros de GitHub Actions. | Secret scan en cada PR y logs sanitizados: no imprimir variables sensibles, tokens, cabeceras `Authorization` ni cookies; usar sólo fixtures sintéticos. | `git grep -n -I -E '(AKIA[0-9A-Z]{16}|gh[pousr]_[A-Za-z0-9_]{20,}|BEGIN (RSA|EC|OPENSSH) PRIVATE KEY|password=|token=)' -- . ':(exclude)docs/ci-threat-model.md'`; revisar logs de CI y ejecutar `npm test`. | El comando no encuentra credenciales; los logs no contienen secretos; las pruebas usan únicamente los tres registros sintéticos de `src/lib/data/inspections.ts`. | **Alta**: una filtración puede comprometer cuentas y datos fuera del repositorio. | Patrones desconocidos, secretos aportados por terceros o valores en servicios externos pueden evadir el escaneo; requiere revisión humana y rotación inmediata si aparece un hallazgo. |
| El workflow obtiene permisos mayores de los necesarios o un cambio de PR los utiliza para escribir en el repositorio. | Repositorio, tokens de GitHub Actions y artefactos de evaluación. | Permisos mínimos declarados a nivel global: `contents: read`; no conceder escritura salvo una tarea justificada y aislada. | `Select-String -Path .github/workflows/*.yml -Pattern '^permissions:|contents:'`; revisar cada workflow y ejecutar `npm run verify`. | Los workflows declaran como máximo `contents: read`, no usan `write-all`, y el job puede instalar, probar y compilar sin permisos de escritura. | **Alta**: un token excesivo amplía el impacto de una acción comprometida o de una dependencia maliciosa. | Acciones de terceros, runners o permisos de organización pueden introducir riesgo residual; fijar versiones de acciones y revisar cambios de workflow. |
| Una fixture de prueba contiene PII o credenciales reales y termina en la build, caché o reporte. | Fixtures, build estática, cachés y `reports/verification.json`. | Fixtures sintéticos sin credenciales reales; excluir reportes generados del control de versiones; validar campos y revisar artefactos antes de publicar. | `npm test`; `git grep -n -I -E '(@[A-Za-z0-9.-]+\.[A-Za-z]{2,}|\+?[0-9][0-9 ()-]{7,}|AKIA[0-9A-Z]{16}|BEGIN .* PRIVATE KEY)' -- src tests public docs`; `git check-ignore reports/verification.json`. | Las pruebas pasan; sólo aparecen datos sintéticos; no hay coincidencias de PII/secretos en las rutas revisadas; `reports/verification.json` está ignorado. | **Media**: el alcance actual es estático y sintético, pero una fixture copiada puede propagarse a varios artefactos. | Un dato real introducido en `evidence/` o en un artefacto externo puede no estar cubierto por el patrón; revisión manual por PR sigue siendo necesaria. |

## Reglas de aceptación

- No se considera completa una amenaza si carece de activo, control, prueba, resultado esperado, prioridad y riesgo residual.
- Una prueba futura debe permanecer marcada como futura hasta que exista la implementación que pueda ejecutarla.
- La prioridad se justifica por impacto y probabilidad en el flujo: alta para autorización, integridad, secretos y permisos; media para fixtures porque el repositorio actual usa datos sintéticos y no tiene backend.
