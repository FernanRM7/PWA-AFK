## Integrante: Kevin Rojas Martinez — Service Worker y evidencia de Semana 3

- **Contribución concreta y enlace:** implementé el ciclo de vida seguro, el precache, el runtime cache, el fallback offline, la invalidación controlada y la recuperación ante fallos en [`public/sw.js`](../blob/feat/service-worker/public/sw.js). Documenté la estrategia y sus límites en [`docs/cache-strategy.md`](../blob/docs/evidence-week03/docs/cache-strategy.md), y añadí las pruebas deterministas en [`tests/service-worker.spec.ts`](../blob/feat/service-worker/tests/service-worker.spec.ts). La contribución base está en el commit [`ba37952`](https://github.com/FernanRM7/PWA-AFK/commit/ba37952).
- **Decisión que puedo explicar y por qué:** separé el precache y el runtime cache usando nombres versionados (`afk-precache-v1` y `afk-runtime-v1`). La limpieza de versiones antiguas ocurre solo en `activate` y después de comprobar el precache actual, para que una actualización fallida no destruya la versión válida. Excluí métodos distintos de `GET`, otros orígenes, rutas sensibles y solicitudes con `Authorization`, `Cookie` o `Cache-Control: no-store` para evitar cachear datos sensibles o PII.
- **Comandos o pruebas ejecutadas:** `npm run test:vitest -- tests/service-worker.spec.ts`, `npm run test:vitest`, `npx tsc --noEmit`, `npm run verify`, `make verify` y `bash public-tests/check.sh`.
- **Resultado real observado:** la suite específica reportó 5 pruebas pasadas; la suite Vitest completa reportó 3 archivos y 11 pruebas pasadas; TypeScript terminó sin errores. Las pruebas verifican instalación, activación, limpieza controlada, fetch, fallback de navegación offline, exclusión de solicitudes sensibles y conservación de la caché anterior cuando falla una actualización.
- **Regresión que detectan las pruebas:** fallan si no se crea el precache, si `activate` elimina una caché ajena o no elimina una versión antigua, si una navegación offline no devuelve la shell, si una solicitud sensible se guarda o si una actualización fallida elimina la caché previa.
- **Limitación, dificultad o riesgo identificado:** el conjunto usa APIs simuladas y datos sintéticos; no prueba diferencias entre navegadores, instalación real, DevTools, Background Sync ni sincronización con backend. El fallback devuelve `503` si nunca se precacheó la shell. La evidencia de CI debe tomarse del workflow y SHA reales de GitHub Actions; el reporte local no prueba CI.

Revisé el código, ajusté las exclusiones de privacidad, ejecuté las pruebas y validé personalmente los resultados reportados; no presento como ejecutado ningún resultado que no haya sido comprobado.
